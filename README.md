# GameEdge

面向游戏房间服务的 C++20 TCP 长连接网关实验项目。当前支持单上游兼容模式与静态多房间路由。它用于练习非阻塞网络 I/O、连接生命周期与背压；尚未完成性能调优，也未声称达到生产级低延迟。

## 架构

```text
玩家客户端 ── TCP 帧 ──> GameEdge ── TCP 帧 ──> 房间服务 0/1/…
                       │
                       ├─ epoll（Linux）/ WSAPoll（Windows 开发测试）
                       ├─ 流式分帧与心跳
                       ├─ 每方向写缓冲区上限 1 MiB
                       └─ 空闲超时与优雅退出
```

网关只解释帧类型，数据帧负载保持不透明。客户端 Ping 在网关得到 Pong，不转发到房间服务。每条客户端连接最多对应一条上游连接；上游出错只关闭该会话。每次可读事件最多执行 16 次 8 KiB 读取，避免繁忙连接独占事件循环。上游在背压暂停期间关闭时，网关暂时移除其轮询注册，待客户端缓冲区降到低水位后继续读取。监听地址固定为 `127.0.0.1`，便于本地开发。

## 协议

每帧是 `4 字节大端长度 | 1 字节类型 | 负载`。长度包含类型字节，不包含自身。`0x01` 是数据，`0x02` 是 Ping，`0x03` 是 Pong，`0x04` 是选房。Ping/Pong 无负载，选房负载是 4 字节大端无符号房间 ID，数据负载最大 64 KiB。非法帧关闭该客户端会话。TCP 拆包和粘包由流式解码器处理。

多房间模式要求先发送一次选房帧，然后才能发数据。网关按 `房间 ID % 房间服务数量` 选择上游，并在连接生命周期内固定该路由。选房帧只由网关处理。重复选房或在选房前发送数据会关闭该会话。Ping 可在选房前使用。房间端口列表在启动时固定；增减端口会改变取模映射，尚无会话迁移或房间目录服务。

## 构建与运行

需要 C++20 编译器、CMake 3.16+ 和 Python 3。Linux 使用 `epoll`；Windows 使用 `WSAPoll` 运行相同行为测试。

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
```

开两个终端：

```bash
python scripts/mock_room.py --port 9001
./build/game_edge 9000 127.0.0.1 9001
```

Windows 可运行 `build/Release/game_edge.exe`（多配置生成器）或实际构建产物所在路径。可选 `--idle-ms 30000` 调整客户端空闲时间；默认 30 秒。按 Ctrl+C 停止接收新连接，最多等待 5 秒关闭现有会话。退出时在标准错误输出会话与字节计数。

多房间模式在本机启动多个房间服务后运行：

```bash
python scripts/mock_room.py --port 9001
python scripts/mock_room.py --port 9002
./build/game_edge 9000 --rooms 9001,9002
```

此模式的上游地址固定为 `127.0.0.1`。例如房间 ID `1` 会路由到第二个端口。旧的单上游命令无需发送选房帧。

## 压测

先启动模拟房间服务和网关，再运行：

```bash
python scripts/bench.py --port 9000 --clients 16 --requests 100 --payload-bytes 128
```

脚本输出环境、并发量、总请求数、吞吐和 P50/P99 请求往返延迟。它是本机顺序请求/响应工作负载，不等于生产游戏流量，也不自动与其他网关进行公平比较。请保存原始 JSON、机器规格和构建参数后再在简历中引用数字。

可用同一工作负载重复测直连模拟房间服务与经网关的结果：

```bash
python scripts/run_experiment.py --gateway-bin ./build/game_edge --clients 16 --requests 100 --payload-bytes 128 --rounds 3 > experiment.json
```

脚本自动启动本机模拟房间服务与网关，按每轮“直连、经网关”的顺序运行并保存原始 JSON。两组结果不能直接解释为网关的纯开销：Python 房间服务、客户端调度、系统噪声与顺序效应都在测量内；需要增加预热、交换测量顺序和更真实的负载后才能做性能结论。

## 当前边界与后续方向

当前没有 TLS、认证、UDP、动态房间目录或集群控制。单事件循环中还需用 Linux 压测与 profiler 验证性能瓶颈，才能判断是否增加多 reactor、批量发送或更细的内存管理。后续优先做真实负载与故障场景测试，不预设优化能带来的提升。

## 项目用途

此仓库展示网关实现和设计取舍。面试时可以围绕分帧、非阻塞连接、慢客户端背压、上游故障隔离、静态房间路由与可复现压测讨论，不应把模拟房间服务描述成完整游戏服务器。
